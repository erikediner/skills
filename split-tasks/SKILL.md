# split-tasks

You break a specification down into small, independent tasks. Each task is a
**tracer bullet**: a thin vertical slice that goes through every layer (DB,
API, UI, test) and can be demonstrated on its own.

## Step 1: Gather the basis

Ask the developer to point to the task folder `docs/tasks/<task-id>/` (from
`grill-spec`). Read all of `SPEC.md`. Explore the affected code if you have not
already. Use the same terms as the spec.

## Step 2: Draw the vertical slices

Break the work into tracer bullet tasks by these rules:

- Each slice delivers a narrow but **complete** path through every layer
- A finished slice can be demoed or verified on its own
- Prefer many thin slices over a few thick ones
- Mark each task **HITL** (needs a human decision or review) or **AFK** (can
  be implemented without interruption). Prefer AFK.

## Step 3: Check with the developer

Show the draft as a numbered list. For each task:

- **Title**
- **Type**: HITL / AFK
- **Blocked by**: other tasks (if any)
- **Covers**: which user stories from the spec

Then call `grilling`. Topic: is the granularity right (too coarse or too
fine), are the dependencies right, should some tasks be merged or split
further, are HITL and AFK marked correctly. Iterate until the developer
approves.

## Step 4: Write the kanban file

Save as `docs/tasks/<task-id>/TASKS.md` using the template in
[TASKS-TEMPLATE.md](TASKS-TEMPLATE.md). Use the same `<task-id>` as the spec.

Include:
- A link to `SPEC.md` (relative, same folder)
- Kanban columns: **Ready** / **In progress** / **Done**
- A mermaid diagram showing the dependencies between tasks
- Today's date in `<!-- Generated by AI with human supervision. Last updated: [DATE] -->`

## Step 5: Idempotence

If the file already exists: read it, keep the status (In progress/Done) of
existing tasks, and merge in new ones without overwriting work already done.
